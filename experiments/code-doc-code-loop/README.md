# 实验：代码-文档-代码循环验证

> 实验日期：2026-08-16
> 实验室：quanttide-laboratory-of-software-engineering

## 假设

**代码-文档-代码循环**成立：以"文档 = 代码的镜像"为机制，通过**提取器**（代码→文档自动生成）与**契约测试**（文档↔代码一致性校验）形成闭环——代码演进自动反映到文档，文档偏差可被测试捕获。

```
代码 ──提取器──→ 文档
  ↑                │
  └──契约测试红灯──┘（代码变更或文档偏差 → 红灯 → 修正 → 绿）
```

## 装置（最小实验）

```
code-doc-code-loop/
├── src/calculator.py      # 实验对象：微型计算器模块（4 函数）
├── scripts/extract_api.py # 提取器：AST 提取函数签名 → 生成 docs/api.md
├── docs/api.md            # 文档（代码的镜像——由提取器生成）
└── tests/contract_test.py # 契约测试：解析 docs/api.md 声明的 API ↔ 代码实际导出
```

## 实验步骤（验证循环三个环节）

### 环节 A：代码 → 文档（提取）

1. `src/calculator.py` 实现 add/sub/mul/div 四个函数
2. `scripts/extract_api.py` 用 Python AST 提取函数签名 → 生成 `docs/api.md`（函数名/参数/文档字符串）

### 环节 B：文档 → 代码（契约测试驱动）

3. `tests/contract_test.py`：解析 `docs/api.md`（文档声明的 API）与代码实际导出对比：
   - 文档声明的每个函数必须存在于代码（反之亦然）
   - 参数签名必须一致
4. 初始状态：提取生成 → 契约测试 **绿**

### 环节 C：闭环验证（关键实验）

5. **代码演进 → 红灯**：给 calculator 加一个 `power` 函数（不改文档）→ 契约测试应**红灯**（代码有文档没有的函数）
6. **重新提取 → 绿**：运行提取器更新文档 → 契约测试**绿**（循环闭合：代码演进自动反映到文档）
7. **文档偏差 → 红灯**：手动改 docs/api.md（如删掉 div）→ 契约测试应**红灯**（文档与代码不一致被捕获）
8. **修正 → 绿**：恢复文档 → 绿

## 成功标准

| # | 标准 | 验证方式 |
|---|------|---------|
| 1 | 提取器能从代码生成准确文档 | 环节 A 生成的 api.md 与代码一致 |
| 2 | 契约测试能捕获"代码有文档无"的偏差 | 步骤 5 红灯 |
| 3 | 契约测试能捕获"文档有代码无"的偏差 | 步骤 7 红灯 |
| 4 | 循环闭合：重新提取即恢复绿 | 步骤 6 绿 |
| 5 | 全流程可重复（脚本化） | 一键 `make verify` 或脚本 |

### 循环成立的机制（实验证据）

```
代码演进（+power）→ 契约测试红灯（代码有文档无）
→ 运行提取器 → 文档镜像更新 → 绿灯（闭环闭合）
→ 手动改文档（删 div）→ 红灯（文档偏差被捕获）→ 重提取 → 绿
```

**三个环节的有效性**：
1. **代码→文档（提取器）**：AST 提取准确、成本极低——"文档是代码的镜像"成立
2. **文档→代码（契约测试）**：双向校验（代码有文档无 + 文档有代码无 + 签名不一致）——偏差全覆盖
3. **闭环**：提取器是"恢复绿"的唯一手段——强制文档与代码同步，人工改文档必然红灯

### 扩展到真实代码库的可行性

- **提取器**：AST 提取对 Python 有效；多语言需对应解析器（qtcloud-code CLI 的 multi-language graph 可承担）
- **契约粒度**：本实验校验 API 签名级；真实代码库可扩展校验行为级（测试用例即文档）
- **文档形态**：函数列表 → 可扩展为模块图/调用图（代码→文档的图文档）

### 结论

**代码-文档-代码循环成立**：提取器 + 契约测试构成最小闭环，代码演进自动同步文档，文档偏差被测试捕获。适合作为 qtcloud-code 重新设计的核心机制。
